# Day 4 Boss 答案

## 1. Tool 是谁执行的？LLM 能不能直接执行 Tool？

**Tool 是程序（你的代码）执行的，LLM 不能直接执行 Tool。**

**详细解释**：

LLM 的能力边界：
- ✅ 理解用户意图
- ✅ 从可用工具列表中选择合适的工具
- ✅ 生成工具调用参数（tool_name + arguments）
- ❌ **不能**真正执行工具代码
- ❌ **不能**调用外部 API
- ❌ **不能**操作数据库

**为什么 LLM 不能执行工具？**
- LLM 是纯文本生成模型，只能输出 token 序列
- 它没有"执行"能力，没有运行时环境
- 它的"调用工具"只是输出一个 JSON，表示"我想调用这个工具"

**执行流程**：
```
LLM 输出: {"tool": "get_weather", "arguments": {"city": "北京"}}
    ↓
你的代码解析这个 JSON
    ↓
你的代码调用: get_weather(city="北京")
    ↓
你的代码拿到结果: "北京今天晴，25°C"
    ↓
你的代码把结果发给 LLM
    ↓
LLM 生成最终回复
```

**这是 Agent 系统最重要的设计原则**：
- LLM 是"大脑"，负责决策
- 程序是"手脚"，负责执行
- 两者协作，缺一不可

## 2. Tool Definition 的作用是什么？

**Tool Definition 是 LLM 和程序之间的"契约"。**

**作用**：

1. **告诉 LLM 有哪些工具可用**：LLM 根据 description 判断什么时候该用这个工具
2. **定义参数格式**：parameters（JSON Schema）告诉 LLM 应该传什么参数
3. **程序解析的依据**：程序根据 tool_name 找到对应的执行代码

**Tool Definition 的三个核心字段**：

| 字段 | 作用 | 谁看 |
|------|------|------|
| name | 工具唯一标识 | LLM + 程序 |
| description | 什么时候用、怎么用 | **LLM 主要看这个** |
| parameters | 参数格式 | LLM + 程序 |

**description 是 Tool Definition 中最重要的部分**：
- 它是 LLM 决定是否调用这个工具的唯一依据
- 写得好 → LLM 准确选择工具
- 写得差 → LLM 选错工具或漏选

**好的 description 示例**：
```
"获取指定城市的实时天气信息，包括温度、天气状况、湿度。当用户询问天气、气温、是否下雨时使用。"
```

**差的 description 示例**：
```
"天气工具"
```

## 3. 如果 LLM 决定调用一个不存在的工具怎么办？

**这是边界情况，必须有处理策略。**

**可能的原因**：
- LLM 产生了幻觉，编造了一个工具名
- Tool Definition 写得误导了 LLM
- 模型能力不足

**处理策略**：

1. **检查工具是否存在**：
```python
tool_map = {tool.name: tool for tool in ALL_TOOLS}
if tool_name not in tool_map:
    return f"错误: 工具 '{tool_name}' 不存在。可用工具: {list(tool_map.keys())}"
```

2. **把错误反馈给 LLM**：
   - 把"工具不存在"的错误信息作为 tool result 发给 LLM
   - LLM 通常会道歉并重新选择

3. **重试机制**：
   - 如果 LLM 重新选择，继续执行
   - 如果连续失败 N 次，返回错误给用户

4. **监控告警**：
   - 记录"工具不存在"的发生率
   - 如果某个工具频繁被错误调用，优化 description

## 4. 工具执行出错了怎么处理？

**工具执行出错是常态，必须有完整的错误处理。**

**常见错误类型**：
- 参数错误（缺少参数、类型不对）
- 执行错误（网络超时、API 报错）
- 业务错误（城市不存在、股票不存在）

**处理策略**：

1. **捕获异常，返回错误信息**：
```python
try:
    result = tool.execute(**arguments)
except Exception as e:
    result = f"工具执行错误: {e}"
```

2. **把错误反馈给 LLM**：
   - 关键：让 LLM 知道工具失败了
   - LLM 可能选择重试、换工具、或直接告诉用户

3. **重试机制**：
   - 可恢复错误（网络超时）：自动重试 1-2 次
   - 不可恢复错误（参数错误）：直接反馈给 LLM

4. **优雅降级**：
   - 如果天气工具失败，告诉用户"暂时无法获取天气"
   - 不要让用户看到一堆报错

**错误信息要给 LLM，不要吞掉**：
```
❌ 错误做法: 工具失败了，程序默默返回空字符串
✅ 正确做法: 返回 "错误: 天气API超时，请稍后重试"
   → LLM 看到这个错误，会告诉用户"天气服务暂时不可用"
```
