# Day 5 Boss 答案

## 1. Agent Loop 为什么可能死循环？

**死循环的常见原因**：

1. **LLM 反复调用同一个工具**：
   - 工具结果不符合预期，LLM 想"再试一次"
   - 但工具本身没问题，是 LLM 的参数有问题
   - 结果：同样的调用重复 N 次

2. **LLM 在两个工具间来回调用**：
   - 调用工具 A → 结果不理想 → 调用工具 B → 结果也不理想 → 又调用工具 A
   - 形成 A → B → A → B 的循环

3. **LLM 没有明确的"结束"信号**：
   - 任务已经完成，但 LLM 觉得"还可以做得更好"
   - 继续调用工具，但已经没有新信息了

4. **工具结果被忽略**：
   - LLM 可能"忘记"了之前的工具结果
   - 重复调用同样的工具获取同样的信息

**实际案例**：
```
用户: "今天北京天气怎么样"
Agent: 调用 get_weather("北京") → "北京晴，25°C"
Agent: 觉得不够详细，调用 get_weather("北京") → "北京晴，25°C"
Agent: 还是不够，调用 get_weather("北京") → "北京晴，25°C"
...（死循环）
```

## 2. 如何检测并终止无效循环？

**核心策略：Max Iterations（最大迭代次数）**

```python
while not finished and iteration < max_iterations:
    # Agent Loop
    iteration += 1
```

**Max Iterations 设多少合适？**
- 简单任务（单工具）：3-5 次
- 中等任务（2-3个工具）：5-8 次
- 复杂任务（多工具协作）：8-15 次
- 一般默认：10 次

**其他检测策略**：

1. **重复检测**：
   - 如果连续 3 次调用同一个工具且参数相同 → 强制结束
   - 如果工具调用序列出现循环模式 → 强制结束

2. **Token 预算**：
   - 设置单次会话的 Token 上限
   - 超出后强制结束

3. **时间限制**：
   - 设置单次会话的超时时间（如 60 秒）
   - 超时后强制结束

4. **人工介入**：
   - 高价值任务设置"人工审批"节点
   - 超过 N 次迭代后暂停，等待人工确认

## 3. Tool 执行失败时 Agent 应该怎么处理？

**处理流程**：

```
工具执行失败
    ↓
捕获异常，生成错误信息
    ↓
把错误信息作为 tool result 发给 LLM
    ↓
LLM 看到错误，决定下一步：
    ├── 重试（换参数）
    ├── 换工具
    ├── 直接告诉用户
    └── 继续其他任务
```

**关键原则**：

1. **不要吞掉错误**：
   - ❌ 返回空字符串
   - ✅ 返回 "错误: 天气API超时，请稍后重试"

2. **让 LLM 知道失败了**：
   - LLM 需要错误信息才能做出正确决策
   - 如果吞掉错误，LLM 会以为工具成功了

3. **区分可恢复 vs 不可恢复错误**：
   - 可恢复（网络超时）：自动重试 1-2 次
   - 不可恢复（参数错误）：直接反馈给 LLM

4. **记录失败**：
   - 在 AgentState 中记录 tool_call 的 success=False
   - 用于后续分析和优化

## 4. Max Iterations 设多少合适？

**没有固定值，取决于任务复杂度**：

| 任务类型 | 建议 Max Iterations | 原因 |
|----------|---------------------|------|
| 单工具调用 | 3-5 | 一次调用就能完成 |
| 多工具顺序调用 | 5-8 | 需要 2-3 个工具协作 |
| 多工具并行+汇总 | 8-12 | 并行调用 + 汇总分析 |
| 复杂研究任务 | 10-15 | 需要多轮搜索和分析 |

**实际考虑因素**：

1. **成本**：每次迭代都消耗 Token，Max Iterations 越大成本越高
2. **用户体验**：迭代越多，等待时间越长
3. **任务复杂度**：复杂任务需要更多迭代
4. **模型能力**：强模型可能 1-2 次就完成，弱模型可能需要更多次

**生产环境建议**：
- 默认 10 次
- 根据任务类型动态调整
- 监控实际迭代次数分布
- 如果大部分任务都在 3 次内完成，可以降到 5 次
