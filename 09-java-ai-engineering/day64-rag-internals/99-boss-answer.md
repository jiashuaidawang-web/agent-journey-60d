# Day 64 Boss 答案

## 1. 余弦相似度、内积、L2 距离三种度量有什么区别？各自适用场景？

**余弦相似度（Cosine Similarity）**：
- 公式：cos(A,B) = A·B / (‖A‖·‖B‖)
- 取值范围：[-1, 1]，值越大越相似
- 特点：只关心方向，不关心长度
- 适用场景：**文本语义检索**（最常用），因为文本向量长度受文本长度影响，但语义由方向决定

**内积（Inner Product / Dot Product）**：
- 公式：A·B = ΣAi·Bi
- 取值范围：(-∞, +∞)
- 特点：同时受方向和长度影响
- 适用场景：**推荐系统**（向量长度代表热度/权重）
- 注意：向量归一化后，内积 = 余弦相似度

**L2 距离（欧氏距离）**：
- 公式：‖A-B‖ = √Σ(Ai-Bi)²
- 取值范围：[0, +∞)，值越小越相似
- 特点：关心空间中两点的绝对距离
- 适用场景：**图像特征检索**、人脸识别

**对 RAG 的启示**：
- 文本 Embedding 通常归一化，用内积即可
- 不同模型的训练目标不同，选择对应的度量方式
- 例如 OpenAI text-embedding-3 推荐用余弦相似度

## 2. HNSW 算法的核心思想是什么？搜索过程是怎样的？

**HNSW（Hierarchical Navigable Small World）** 的核心思想是**构建多层导航图**：

**层级结构**：
- 类似跳表（Skip List），每个节点以概率 p 出现在上一层
- Layer 0：所有节点，连接密集（精确搜索）
- Layer 1：部分节点，连接中等
- Layer 2：更少节点，连接稀疏（快速定位）

**搜索过程**：
1. 从最高层的入口点开始
2. 在当前层贪心搜索，找到最近节点
3. 下降到下一层，以上一层的最近节点为入口
4. 重复直到 Layer 0
5. 在 Layer 0 返回 Top-K 最近邻

**关键参数**：
- `M`：每个节点的最大连接数（默认 16），影响图连通性
- `efConstruction`：构建时的搜索宽度（默认 200），越大索引质量越高
- `efSearch`：搜索时的搜索宽度（默认 50），越大召回率越高

**复杂度**：
- 构建：O(N log N)
- 搜索：O(log N)
- 空间：O(N × M)

**和暴力检索对比**：
- 暴力检索：O(N)，100 万向量需要 100 万次距离计算
- HNSW：O(log N)，100 万向量只需约 1000 次距离计算
- 速度快 1000 倍，召回率 > 95%

## 3. IVF + PQ 组合是如何加速检索的？

**IVF（Inverted File Index）** 加速原理：
1. 用 K-Means 对向量空间聚类，得到 K 个中心点（Centroid）
2. 每个向量分配到最近的聚类
3. 搜索时，先找到查询向量最近的 nprobe 个聚类
4. 只在这 nprobe 个聚类内暴力检索
5. 搜索范围从 N 降到 N/K × nprobe

**PQ（Product Quantization）** 加速原理：
1. 将 D 维向量分成 m 段，每段 D/m 维
2. 对每段用 K-Means 聚类，得到 256 个聚类中心（1 字节）
3. 每段用最近的聚类中心代替，存储从 D×4 字节降到 m×1 字节
4. 距离计算用查表法，速度提升 10 倍

**IVF-PQ 组合**：
- IVF 减少搜索范围（从 N 到 N/K × nprobe）
- PQ 加速距离计算（从浮点到查表）
- 组合后速度提升 100+ 倍，召回率约 90-95%

**对 RAG 的启示**：
- 小规模数据（< 10 万）：用 HNSW（精确）
- 大规模数据（> 100 万）：用 IVF-PQ（高效）
- 超大规模（> 1 亿）：用 DiskANN（磁盘索引）

## 4. 向量数据库如何选型？各自适用场景是什么？

**选型矩阵**：

| 数据库 | 类型 | 优势 | 劣势 | 适用场景 |
|--------|------|------|------|----------|
| PGVector | PG 插件 | 和 PG 一体，支持 SQL 过滤 | 性能一般 | 中小规模，已有 PG |
| Milvus | 专用 | 分布式，大规模，功能全 | 部署复杂 | 大规模企业 |
| Qdrant | 专用 | Rust 高性能，过滤强 | 社区较小 | 高性能单机 |
| Weaviate | 专用 | 多模态，GraphQL | 学习曲线 | 多模态应用 |
| Chroma | 专用 | 简单，嵌入式 | 功能少 | 原型开发 |
| Faiss | 库 | 算法丰富，性能强 | 无服务化 | 算法研究 |

**选型建议**：
- **原型开发**：Chroma（最简单）
- **中小企业（< 100 万向量）**：PGVector（和 PG 一体）
- **中大型企业（100 万 - 1 亿向量）**：Milvus / Qdrant
- **超大规模（> 1 亿向量）**：Milvus 分布式
- **多模态**：Weaviate
- **算法研究**：Faiss

**对 RAG 的启示**：
- 向量数据库是 RAG 的基础设施，选型影响整个系统性能
- 生产环境推荐 Milvus 或 Qdrant
- 开发环境推荐 Chroma

## 5. 文档拆分有哪些策略？中文文档拆分有什么特殊之处？

**文档拆分策略**：

**递归拆分（Recursive Splitter）**：
- 按分隔符列表递归切分（\n\n → \n → 。 → . → 空格）
- 如果 chunk 太大，用下一个分隔符继续切
- 适用场景：**通用文档**（最常用）

**语义拆分（Semantic Splitter）**：
- 基于 Embedding 相似度
- 相似句子合并，不同句子分开
- 适用场景：**长文档**，语义完整性要求高

**固定长度拆分（Fixed Length Splitter）**：
- 固定 chunk_size（如 512 token）
- 简单但可能切断语义
- 适用场景：**简单场景**

**中文专属拆分**：
- 按句号（。）切分（中文句子完整）
- 按段落（\n\n）切分
- 按标点（。！？；）切分
- 中文没有空格，不能用空格切分
- 中文 chunk_size 通常 500-800 字

**关键参数**：
- `chunk_size`：每块大小（500-1000 token）
- `chunk_overlap`：重叠大小（50-200 token），保证上下文连续
- `separators`：分隔符（中文：。！？；\n）

**对 RAG 的启示**：
- 拆分质量直接影响检索效果
- 中文文档建议用递归拆分 + 句号分隔符
- chunk_overlap 保证上下文连续，避免切断语义
