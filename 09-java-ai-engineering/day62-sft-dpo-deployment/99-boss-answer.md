# Day 62 Boss 答案

## 1. SFT 的原理是什么？它有什么局限性？

**SFT（Supervised Fine-Tuning）原理**：

SFT 是最常用的微调方法，核心思想是使用标注的"指令-回答"数据，以监督学习的方式训练模型，让模型学会遵循指令并生成符合要求的回答。

**训练流程**：
1. 准备数据：收集"instruction + input → output"的标注数据
2. 构建输入：将 instruction 和 input 拼接作为模型输入
3. 计算 loss：只对 output 部分计算交叉熵损失（不计算 instruction 部分的 loss）
4. 反向传播：更新模型参数（或 LoRA 参数）

**损失函数**：
$$\mathcal{L}_{SFT} = -\sum_{t=1}^{T} \log p_\theta(y_t | y_{<t}, x)$$

其中 $x$ 是指令输入，$y$ 是标注回答。

**SFT 的局限性**：

1. **需要大量标注数据**：高质量的标注数据获取成本高
2. **过拟合标注风格**：模型可能过度模仿标注者的风格，缺乏多样性
3. **无法处理偏好**：SFT 只告诉模型"什么是对的"，不告诉"哪个更好"
4. **泛化能力有限**：对未见过的指令类型可能表现不佳
5. **标注偏差**：标注者的主观偏好会影响模型行为

**适用场景**：
- 任务型对话（翻译、摘要、问答）
- 指令遵循（按格式输出）
- 风格迁移（模仿特定写作风格）

## 2. DPO 和 RLHF 有什么区别？DPO 的优势是什么？

**RLHF（Reinforcement Learning from Human Feedback）**：
- 经典的人类反馈强化学习方法
- 三步流程：SFT → 训练奖励模型（RM）→ PPO 强化学习训练
- 复杂度高，训练不稳定

**DPO（Direct Preference Optimization）**：
- 2023 年提出的简化方法
- 不需要训练奖励模型
- 直接使用偏好数据优化模型

**核心区别**：

| 维度 | RLHF | DPO |
|------|------|-----|
| 步骤数 | 3步（SFT + RM + PPO） | 2步（SFT + DPO） |
| 奖励模型 | 需要训练 | 不需要 |
| 训练算法 | PPO（不稳定） | 监督学习（稳定） |
| 复杂度 | 高 | 低 |
| 超参数 | 多 | 少 |
| 效果 | 好 | 接近 RLHF |

**DPO 的数学原理**：
- 将奖励函数表示为策略函数：$r(x, y) = \beta \log\frac{\pi_\theta(y|x)}{\pi_{ref}(y|x)}$
- 直接优化偏好对的对数几率：
$$\mathcal{L}_{DPO} = -\mathbb{E}\left[\log\sigma\left(\beta\log\frac{\pi_\theta(y_w|x)}{\pi_{ref}(y_w|x)} - \beta\log\frac{\pi_\theta(y_l|x)}{\pi_{ref}(y_l|x)}\right)\right]$$

**DPO 的优势**：

1. **无需奖励模型**：省去了训练 RM 的步骤和成本
2. **训练稳定**：使用监督学习，避免 PPO 的不稳定性
3. **实现简单**：代码量远少于 RLHF
4. **超参数少**：主要只有 $\beta$ 一个超参数
5. **效果接近**：实验表明 DPO 效果接近 RLHF

**DPO 数据格式**：
```json
{
    "prompt": "翻译成英文：你好世界",
    "chosen": "Hello World",
    "rejected": "Hi World"
}
```

## 3. 微调模型的评估指标有哪些？各适用于什么场景？

**自动指标**：

**BLEU（Bilingual Evaluation Understudy）**：
- **适用场景**：机器翻译
- **原理**：计算生成文本和参考文本的 n-gram 精确率
- **分数范围**：0-100（越高越好）
- **优点**：计算快速，与人工评价相关性高
- **缺点**：不考虑语义，只考虑词汇重叠

**ROUGE（Recall-Oriented Understudy for Gisting Evaluation）**：
- **适用场景**：文本摘要
- **原理**：计算生成文本和参考文本的 n-gram 召回率
- **变体**：ROUGE-1（unigram）、ROUGE-2（bigram）、ROUGE-L（最长公共子序列）
- **优点**：对摘要任务效果好
- **缺点**：同 BLEU，不考虑语义

**Perplexity（困惑度）**：
- **适用场景**：语言模型评估
- **原理**：模型对测试集的平均负对数似然
- **分数范围**：越低越好
- **优点**：直接反映模型的语言建模能力
- **缺点**：与生成质量相关性不高

**Accuracy（准确率）**：
- **适用场景**：分类任务
- **原理**：预测正确的样本比例
- **优点**：直观易懂
- **缺点**：不适用于生成任务

**人工评估**：

| 维度 | 说明 | 分数 |
|------|------|------|
| 流畅度 | 生成文本是否通顺 | 1-5 分 |
| 相关性 | 是否回答了问题 | 1-5 分 |
| 准确性 | 信息是否准确 | 1-5 分 |
| 一致性 | 是否与上下文一致 | 1-5 分 |

**评估策略**：
- 自动指标用于快速迭代
- 人工评估用于最终验证
- 两者结合使用效果最佳

## 4. vLLM 和 OLLAMA 部署有什么区别？各自适合什么场景？

**vLLM**：

**核心特性**：
- 高性能推理引擎
- **PagedAttention**：将 KV Cache 分页存储，像操作系统管理内存一样管理显存
- **Tensor Parallelism**：支持多 GPU 张量并行
- **Continuous Batching**：动态批处理，提高吞吐量
- **OpenAI 兼容 API**：可以直接替换 OpenAI API

**适用场景**：
- 生产环境高并发部署
- 需要低延迟的场景
- 多 GPU 分布式部署
- 需要与现有 OpenAI SDK 兼容的场景

**部署步骤**：
1. 合并 LoRA 权重到基座模型
2. 导出为 Hugging Face 格式
3. 启动 vLLM 服务：`python -m vllm.entrypoints.openai.api_server`
4. 通过 OpenAI SDK 调用

**OLLAMA**：

**核心特性**：
- 轻量级本地部署工具
- 支持 Mac/Windows/Linux
- 一键拉取和运行模型
- 支持 GGUF 格式模型
- 内置模型库（Llama、Mistral、Qwen 等）

**适用场景**：
- 本地开发测试
- 小规模部署
- 个人使用
- 快速原型验证

**部署步骤**：
1. 安装 OLLAMA
2. 创建 Modelfile（定义模型配置）
3. 导入模型：`ollama create my-model -f Modelfile`
4. 运行模型：`ollama run my-model`

**对比总结**：

| 维度 | vLLM | OLLAMA |
|------|------|--------|
| 复杂度 | 高 | 低 |
| 性能 | 高 | 中 |
| 并发 | 高 | 低 |
| 部署规模 | 生产级 | 本地/小规模 |
| GPU 支持 | 多 GPU | 单 GPU/CPU |
| 格式 | Hugging Face | GGUF |

## 5. 企业级微调有哪些最佳实践？

**1. 成本控制**

- **使用 LoRA/QLoRA**：相比全量微调，成本降低 10-100 倍
- **选择合适规模的基座模型**：7B 模型足够就用 7B，不要盲目追求大模型
- **使用 Spot 实例**：AWS/GCP 的 Spot 实例价格低 60-90%
- **数据质量 > 数据数量**：1000 条高质量数据可能比 10000 条低质量数据效果好

**2. 效果监控**

- **训练过程监控**：监控 loss 曲线、梯度范数
- **定期评估**：每 N 步评估一次模型效果
- **A/B 测试**：新旧模型对比，用数据说话
- **用户反馈**：收集真实用户反馈，持续优化

**3. 安全合规**

- **数据隐私**：训练数据脱敏，不包含用户隐私信息
- **输出审核**：对模型输出进行安全审核
- **有害内容过滤**：防止模型生成有害内容
- **审计日志**：记录所有训练和推理操作

**4. 模型管理**

- **版本管理**：使用 DVC 或 MLflow 管理模型版本
- **回滚机制**：新版本出问题时可以快速回滚
- **模型注册表**：统一管理所有模型

**5. 持续优化**

- **数据迭代**：持续收集和标注新数据
- **模型迭代**：定期重新训练模型
- **评估迭代**：持续优化评估指标
- **部署迭代**：持续优化部署架构

**6. 团队协作**

- **数据标注规范**：统一标注标准
- **代码规范**：统一的代码风格和文档
- **实验记录**：详细记录每次实验的参数和结果
- **知识共享**：定期分享经验和教训
