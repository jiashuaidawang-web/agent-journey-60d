# Day 7 Boss 答案

## Level 1: 基础概念

### 1. LLM 和 Agent 有什么区别？

**LLM（大语言模型）**：
- 输入：文本 Prompt
- 输出：文本补全
- 能力：理解、生成、推理
- 限制：不能执行代码、不能调用外部 API、不能记住上一次对话

**Agent（智能体）**：
- 输入：用户任务
- 输出：完成任务（可能调用多个工具）
- 能力：LLM + 工具 + 记忆 + 状态 + 循环
- 特点：能自主执行多步任务

**核心区别**：

| 维度 | LLM | Agent |
|------|-----|-------|
| 输入 | 文本 | 任务 |
| 输出 | 文本 | 任务结果 |
| 工具 | 无 | 有 |
| 记忆 | 无 | 有 |
| 状态 | 无 | 有 |
| 循环 | 单次 | 多步 |

**一句话**：Agent = LLM + Tools + Memory + State + Loop

### 2. Agent 和 Workflow 有什么区别？

**Workflow（工作流）**：
- 预定义的步骤和分支
- 开发者写清楚每一步做什么
- 确定性高，可控性强
- 例如：if 天气好 → 推荐户外活动；else → 推荐室内活动

**Agent**：
- LLM 自主决策下一步做什么
- 开发者只定义工具和约束
- 灵活性强，但可控性弱
- 例如：LLM 自己决定先查天气，再决定推荐什么

**核心区别**：

| 维度 | Agent | Workflow |
|------|-------|----------|
| 决策者 | LLM | 开发者 |
| 确定性 | 低 | 高 |
| 灵活性 | 高 | 低 |
| 适用场景 | 开放任务 | 明确流程 |

**实际选择**：
- 流程明确 → Workflow（如审批流程）
- 需要推理 → Agent（如研究分析）
- 实际系统通常是混合：Workflow 框架 + Agent 节点

### 3. Tool Calling 到底是谁决定调用 Tool？

**LLM 决定调用哪个 Tool，程序负责执行。**

详细流程：
1. 程序发送消息 + 工具定义给 LLM
2. LLM 根据用户意图和工具描述，决定调用哪个工具
3. LLM 输出 tool_call（工具名 + 参数）
4. 程序解析 tool_call，执行对应的工具代码
5. 程序把工具结果反馈给 LLM
6. LLM 根据结果继续推理或回复

**关键认知**：
- LLM 不能直接执行工具代码
- LLM 只是输出"我想调用 XX 工具"
- 真正的执行必须由程序完成

### 4. Agent Loop 为什么可能死循环？

**死循环的原因**：
1. LLM 反复调用同一个工具（工具结果不符合预期，想再试）
2. LLM 在两个工具间来回调用（A → B → A → B）
3. LLM 没有明确的结束信号（任务完成了但觉得"还可以更好"）
4. 工具结果被忽略（LLM 忘了之前的结果）

**防止策略**：
- Max Iterations（最大迭代次数）：强制限制循环次数
- 重复检测：连续 3 次相同调用 → 强制结束
- Token 预算：超出预算 → 强制结束
- 时间限制：超时 → 强制结束

## Level 2: 深入理解

### 5. Context 和 Memory 有什么区别？

**Context（上下文）**：
- 范围：单次请求的所有输入
- 生命周期：当前请求
- 内容：System Prompt + 用户输入 + 对话历史 + 检索结果 + 工具结果
- 限制：受 Context Window 限制

**Memory（记忆）**：
- 范围：跨会话持久化
- 生命周期：长期保存
- 内容：用户偏好、历史摘要、关键事实
- 限制：理论上无限

**类比**：
- Context = Java 方法的参数 + 局部变量
- Memory = 数据库 + 缓存

### 6. 为什么 Agent 需要 State？

**State（状态）** 记录 Agent 运行过程中的所有信息：
- 消息历史
- 工具调用记录
- Token 消耗
- 迭代次数
- 完成状态

**为什么需要**：
1. **追踪进度**：知道 Agent 现在在第几步
2. **防止死循环**：通过迭代次数判断是否该停止
3. **错误处理**：记录错误信息，决定下一步
4. **可观测性**：统计 Token 消耗、工具调用次数
5. **断点续跑**：状态持久化后，中断后可以恢复

### 7. 为什么 Agent 不能无限保留历史消息？

1. **Context Window 有限**：即使是 128K 模型也放不下几个月对话
2. **成本爆炸**：历史越长，每次请求成本越高
3. **注意力稀释**：模型难以从超长历史中找到关键信息
4. **Lost in the Middle**：模型对中间部分注意力下降

### 8. Tool Schema 为什么重要？

Tool Schema（Tool Definition）是 LLM 和程序之间的契约：
- 告诉 LLM 有哪些工具可用
- 定义每个工具的参数格式
- LLM 根据 description 决定什么时候调用

**好的 description** 是 Tool Schema 中最重要的部分：
- 写得好 → LLM 准确选择工具
- 写得差 → LLM 选错或漏选

## Level 3: 架构设计

### 9. 如果 Tool 执行失败怎么办？

1. 捕获异常，返回错误信息给 LLM
2. LLM 看到错误，决定重试 / 换工具 / 告诉用户
3. 记录失败（State 中标记 success=False）
4. 如果是可恢复错误（网络超时），自动重试 1-2 次

**关键**：不要把错误吞掉，要让 LLM 知道失败了。

### 10. 如果 LLM 连续调用 Tool 50 次怎么办？

**Max Iterations 保护**：
- 设置最大迭代次数（通常 10 次）
- 达到后强制结束
- 返回错误信息给用户

**其他策略**：
- 重复检测：连续 3 次相同调用 → 强制结束
- Token 预算：超出预算 → 强制结束
- 人工介入：高价值任务暂停等待确认

### 11. Agent 如何支持多模型？

**Model 抽象接口**：
```python
class Model(ABC):
    def chat(self, messages) -> dict: ...
    def chat_with_tools(self, messages, tools) -> dict: ...
```

**不同实现**：
- OpenAIModel
- AnthropicModel
- QwenModel
- DeepSeekModel

**Model Router**：根据成本/延迟/能力选择模型。

### 12. Agent 如何统计 Token？

**TokenCounter**：
- 每次调用 Model 后，累加 input_tokens 和 output_tokens
- 用于成本核算和优化

### 13. Agent 如何恢复中断任务？

**状态持久化**：
- 把 AgentState 序列化到数据库/文件
- 恢复时反序列化，继续执行

**Checkpoint 机制**：
- 每次工具调用后保存状态
- 中断后从最近的 Checkpoint 恢复

## Level 4: 企业级设计

### 14. 企业级 Agent Runtime 设计

```
             Agent Runtime
                  │
      ┌───────────┼───────────┐
      ↓           ↓           ↓
    Model        Tool        Memory
      │           │           │
      └───────────┼───────────┘
                  ↓
             Agent Loop
                  ↓
               State
                  ↓
             Observability
```

**每个模块为什么存在**：

| 模块 | 职责 | 为什么需要 |
|------|------|------------|
| Model | 模型抽象 | 支持多模型切换、Model Router |
| Tool | 工具系统 | Agent 与外部世界交互的唯一方式 |
| Memory | 记忆 | 跨会话记住用户偏好和历史 |
| Agent Loop | 核心循环 | 驱动 LLM → 工具 → LLM 的循环 |
| State | 状态 | 追踪进度、防止死循环、支持恢复 |
| Observability | 可观测性 | 统计 Token、监控性能、排查问题 |

**企业级扩展**：
- 多租户隔离
- 权限控制
- 成本核算
- 全链路追踪
- 断点续跑
- Human-in-the-loop
