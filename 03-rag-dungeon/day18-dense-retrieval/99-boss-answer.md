# Day 18 Boss 答案

## 1. 稠密检索的流程是什么？

```
用户查询
    ↓
[Embedding Model] → 查询向量（如 1024 维）
    ↓
[Vector DB] → 计算查询向量与所有文档向量的相似度
    ↓
[排序] → 按相似度降序排列
    ↓
[Top-K] → 返回最相似的 K 个文档
```

**关键步骤**：
1. **离线**：文档嵌入 → 存入向量数据库
2. **在线**：查询嵌入 → 相似度搜索 → Top-K 结果

## 2. 为什么需要 Embedding？

- 文本无法直接进行数学运算
- Embedding 将文本映射到向量空间
- 语义相似的文本，向量也相似
- 通过向量相似度衡量语义相似度

**没有 Embedding 的替代方案**：
- 关键词匹配（BM25）：无法理解语义
- 无法处理同义词、改写、多语言

## 3. Top-K 的 K 如何选择？

| K 值 | 优势 | 劣势 |
|------|------|------|
| 小（3-5） | 精确 | 可能漏掉相关文档 |
| 中（5-10） | 平衡 | 通用 |
| 大（10-20） | 召回率高 | 噪声多 |

**选择建议**：
- 问答场景：3-5（精确匹配）
- 总结场景：5-10（需要更多上下文）
- 通用：5

**实际考虑**：
- K 越大，LLM 需要处理的上下文越多
- K 越大，Token 成本越高
- 通常配合 Reranker 使用，先大 K 召回，再精排
